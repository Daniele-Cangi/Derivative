# Certified Extension Contract

## Purpose

Derivative is intended to expand through **incrementally certified software domains**, not by treating arbitrary code generation as verified synthesis.

This document defines the minimum architectural and evidentiary contract for extending the Forge verified surface. It is intentionally stricter than the contract for adding a renderer or prompt.

The central rule is:

> An extension may generate more software only when Derivative can also state what was required, what capability was supplied, what evidence was observed, and why an incorrect candidate would fail closed.

## Extension boundary

A certified extension may add one domain, one capability family, or one reusable verification primitive. It should be possible to describe its semantic boundary without naming a specific benchmark case.

Examples of suitable boundaries include:

- a reusable software target or interface contract;
- a reusable input/output behavior such as streaming, ordered transformation, persistence, or schema validation;
- a reusable domain capability whose semantics can be independently checked;
- a verification primitive shared by multiple domains.

A benchmark case, exact function name, fixture value, or one observed failure is not by itself a valid extension boundary.

## Required layers

### 1. Typed requirement representation

The requirement compiler must preserve the semantics needed by downstream planning and verification.

Prefer typed fields, requirement atoms, evidence terms, interface contracts, and capability records over special-case string matching. Lexical recognition may be necessary at the language boundary, but the rest of Forge should consume a typed distinction rather than repeatedly rediscovering the same meaning from prose.

The extension must define which ambiguity is material. If the requested behavior is underspecified in a way that prevents verification, that ambiguity must survive compilation and be able to force `validation_failed`.

### 2. Plan contract

The planner must map the new semantics to explicit structure:

- planned files;
- public interfaces;
- requirement-to-file coverage;
- required tests;
- capability dependencies;
- packaging target;
- validation strategy.

A new domain should not accumulate unrelated branches in `CoderStage`. The current adapter and capability boundaries exist so generation remains replaceable and auditable.

### 3. Generator contract

Generation may be deterministic or model-backed.

A deterministic adapter must:

- implement the declared adapter interface;
- render only planned paths;
- declare only capabilities it actually implements;
- fail rather than silently falling back to a semantically unrelated template.

A model-backed candidate remains untrusted. The complete candidate transaction must stay plan-bound, path-allowlisted, preflighted, provenance-stamped, and independently validated before packaging.

Generated manifests or capability claims from a model are never authoritative.

### 4. Capability contract

Every new behavior that affects the verified claim must be represented as a capability that can be required independently of the generated artifact's own manifest.

`provided_capabilities()` is a claim made by an adapter implementation. It must not return a capability merely because matching prose was seen.

`implements_plan_semantics()` should be true only when the deterministic adapter actually implements the plan's declared semantics. Otherwise the plan should require candidate generation or fail closed according to execution mode.

A capability extension should document:

- semantic meaning;
- requirement evidence that activates it;
- adapter(s) allowed to provide it;
- verification evidence that can establish it;
- expected failure signature when it is absent or contradicted.

### 5. Verification contract

Verification is the authoritative boundary.

A certified extension must identify how an incorrect implementation is rejected without relying only on tests generated by the same process that produced the candidate.

Depending on the capability, acceptable verification may combine:

- executable behavioral checks;
- property-oriented tests;
- interface and AST checks;
- typed requirement coverage;
- dependency and provenance checks;
- resource/isolation checks;
- domain-specific semantic checks;
- independently maintained acceptance oracles;
- proof-oriented handling for universal constraints.

Passing syntax, imports, smoke execution, or candidate-authored tests is not sufficient evidence for a new semantic claim.

Verification code should emit stable failure signatures that describe a structural failure class rather than a benchmark case identifier.

### 6. Evidence and provenance

The extension must preserve the audit path from requirement to packaged artifact.

Relevant evidence should include, where applicable:

- requirement IDs;
- acceptance criteria;
- planned files/tests;
- capability declarations;
- generated-file provenance;
- validation attempts;
- repair directives and changed paths;
- runtime evidence;
- candidate transaction digests;
- external-oracle outcomes.

Repairs remain untrusted revisions. A successful repair must rerun the same authoritative validation boundary rather than inherit the previous candidate's status.

### 7. Evaluation contract

Repository tests prove regression safety; they do not by themselves prove a broader verified claim.

When an extension expands the verified surface, evaluation should include evidence not authored as a direct encoding of the implementation under test. Depending on scope, this may be a held-out case set, an independently written oracle, a sealed benchmark transaction, or another explicitly justified evaluation boundary.

Report provenance must distinguish at least:

- first blind execution;
- held-out evaluation whose contents are repository-known;
- post-fix replay against an already observed bundle;
- ordinary regression testing.

Never silently promote a replay to fresh blind evidence.

## Acceptance checklist

A proposed certified extension is ready for review when all answers below are clear:

- What reusable semantic boundary is being added?
- How is that boundary represented after requirement compilation?
- Which files/interfaces/capabilities does the planner derive from it?
- What does the adapter or candidate compiler generate?
- Which capabilities are authoritative, and who declares them?
- What evidence can reject an incorrect implementation?
- What stable failure signatures are emitted?
- What provenance survives generation and repair?
- What independent or held-out evidence supports expansion of the verified claim?
- What cases remain intentionally unsupported?

If the final question has no answer because the extension is supposed to handle everything, the extension is too broad.

## Preferred direction for generalization

The long-term direction is to reduce semantic knowledge embedded directly in central orchestration modules and move reusable domain knowledge behind typed contracts and extension boundaries.

In practice this means preferring:

- typed requirement features over repeated regex inference downstream;
- capability specifications over domain labels alone;
- composable planning primitives over case-specific file trees;
- reusable semantic validators over benchmark-specific assertions;
- independently testable extension packs over one ever-growing universal adapter.

This does **not** require turning Forge into a plugin framework before the architecture justifies it. Small, explicit seams are preferred over speculative abstraction.

## Benchmark integrity

The current blind-v2 and blind-v3 artifacts and historical reports are evidence and must remain auditable.

Do not modify frozen cases or oracles merely to align them with current implementation behavior. If an oracle is defective, preserve the original artifact and record the defect or adjudication separately.

A known blind case may motivate a structural investigation. It must not become the source for a narrowly tailored renderer, parser rule, validator exception, or expected-output table.

## Non-goals

A certified extension does not need to:

- support every software domain;
- eliminate all model dependence;
- prove arbitrary program correctness;
- make every feasible request `verified`;
- preserve backward compatibility with an incorrect verification claim.

Failing closed on unsupported semantics is valid behavior. The goal is not maximal acceptance. The goal is a larger surface on which `verified` continues to mean something.
